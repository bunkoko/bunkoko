## d10 の答え（短く）
- **d10 は grader ではありません。**
  - grader は、評価セットの CSV の llm_grade 列を後から埋める LLM です（既定は Claude Code の Haiku）。人の点と比べて、検索の良し悪しを測るためのものです。src/koten/eval/grader.py と settings.toml の [llm.grader] で確認しました。
  - d10 は「リランカー」です。検索のたびに動く、小さな別のモデルです（src/koten/retrieve/search.py の CrossEncoderReranker）。
- **「モデルのライセンス」は、リランカーの重みファイルの利用条件です。** 重みファイルは Hugging Face から落とします。台本を書く LLM（Claude や gemma）のライセンスの話ではありません。
  - チャンネルは収益化するので、「非営利のみ」（CC BY-NC など）のモデルは使えません。
  - MIT や Apache-2.0 なら、商用でも使えます。

## リランカー（クロスエンコーダ）とは
- **LLM との違い**
  - LLM は文章を書きます。クロスエンコーダは書きません。
  - 「悩みの文」と「一節」を1組にして読み、合う度合いを1つの数で返すだけです。
  - 多くは BERT 系で、数千万〜6億パラメータほどです。
  - ただし最近は、LLM を元にしたリランカーもあります（Qwen3-Reranker、bge-reranker-v2-gemma）。
- **grader との違い。** grader は評価のための採点役です。リランカーは本番の検索の部品です。
- **埋め込み（e5）との違い**
  - e5 は、悩みと一節を別々に数のベクトルにします。だから速く引けますが、合い方の見方は粗くなります。
  - クロスエンコーダは2つを一緒に読むので、精度が上がります。そのかわり遅くなります。
  - そのため、絞った後の少数にだけ使います。
- **パイプラインの中の位置（コードで確認）**
  1. 3つのクエリで、BM25 と密ベクトルを引きます。権利・注意フラグの絞り込みは、この各検索の中で先にかかります。
  2. RRF でまとめて、上位50件にします（fused_top = 50）。
  3. **ここでリランカーが50組に点を付けて、並べ直します。** 1組は「悩みの文」と「一節の本文＋日本語の要旨」です。
  4. 同じ作品が重ならないように、10件にします。
  5. LLM が、理由をつけて選びます。
- **今の状態。** settings.toml の rerank.model が "要確認" のままです。なので、リランクはしていません。
- **インターネットは要るか**
  - 最初にモデルを落とすときだけ要ります（数百MB〜2GB強。推測）。
  - その後は、キャッシュがあれば HF_HUB_OFFLINE=1 にして、Mac の中だけで動きます（コードで確認）。
  - 悩みの文が外に出ることもありません。
  - 注意：モデルのダウンロードは net.py を通りません（e5 と同じ）。CLAUDE.md の決まりとの関係を、decisions.md に書いておくのがよいと思います（要確認）。
- **大きさと速さ（推測。Mac での実測値は見つかりませんでした）**
  - 小さいモデル（約0.3億〜1億パラメータ）なら、50件で1秒前後と見込みます。
  - bge-reranker-v2-m3（568M）なら、数秒と見込みます。
  - 研究者の報告にあった「small 級＝約0.1億」は誤りです。約1億前後です。
  - koten eval retrieval で測れるのは精度（nDCG）だけで、速さは測れません。速さは別に計ってください（例：time を付けて koten retrieve を回す）。

**Qwen3-Reranker について**

- sentence-transformers 5.6.0 以降の CrossEncoder は、Qwen3-Reranker を読めます（リリースノートと PR #3787、a）。手元の lock は 6.2.0 です。
- ただし、0.6B の LLM 型なので遅めのはずです（推測）。Mac で動くかは要確認です。

**元にしたモデルのライセンス**
- 確認できたもの：

  - tohoku の日本語 BERT：Apache-2.0（a）

**灰色の点：学習データ（MS MARCO）**

- MIT や Apache の表示の義務は、主に重みを配るときにかかります。手元で使うだけなら、ほぼかかりません（推測、要確認）。

## 推奨（推測）
評価セットで、次の3つを比べるのがよいと思います。比べ方は、settings.toml の rerank.model を書き換えて、koten eval retrieval を1回ずつ回します。
- hotchpotch の small-v2 か base-v2：MIT。軽い。
- cl-nagoya/ruri-v3-reranker-310m：Apache-2.0。日本語の点が高いとの報告がある（b）。
- bge-reranker-v2-m3：Apache-2.0。多言語に強い。

注意点：
- 英訳の一節が候補に入る悩みも、評価セットに入れてください。要旨は日本語なので、日本語専用のモデルでもある程度は効くかもしれません（要確認）。
- jina は非営利なので外します。

## 検証で足した点・確かめられなかったこと
- huggingface.co が DNS で開けない。そのため hotchpotch・cl-nagoya・Qwen のモデルカードの license 行と base_model 行は一次資料で読めていない。また、この回の Web 検索の上限（200回）に達し、追加の検索はできなかった。続けるには、huggingface.co をセッションのネットワーク設定で許可するか、Mac で各モデルカードを開いて確かめる必要がある
- small 級の大きさの誤り。「約0.1億」ではなく約1億前後（mMiniLM は埋め込みの部分だけで96M）
- 権利・注意フラグの絞り込みは、RRF の後ではなく各検索の中で先に効いている（planner.py・search.py）
- Qwen3-Reranker は、sentence-transformers 5.6.0 以降の CrossEncoder で読める（リリースノートと PR #3787）。手元の lock は 6.2.0。0.6B・28層の LLM 型なので BERT 型より遅いと見込まれる（推測）。Mac での動作は要確認

- koten eval retrieval が測るのは精度（nDCG）だけ。3つのモデルを比べるには、rerank.model を書き換えて1回ずつ回す。速さは別に計る必要がある（例：time を付けて koten retrieve --worry W0001 --explain を回す）
