## 1. 背景と目的

### 1.1 背景
- Apple Watch では睡眠ステージ・心拍・HRV・呼吸数・手首皮膚温などが自動で記録されるが、**寝室の環境（室温・湿度・CO2・明るさ）との関係**はわからない。
- スマートホームのセンサーを使えば環境は記録できるが、ヘルスケアデータと**同じ時間軸で重ねて見る仕組み**がない。
- 一般的な「寝室は◯℃がよい」といった目安はあるが、**自分にとっての最適値**は、自分のデータを溜めないとわからない。

### 1.2 目的
1. 睡眠と寝室環境を同じ時間軸で**見える化**する。
2. 自分のデータから「どの条件の夜によく眠れているか」の**傾向を見つける**。
3. 就寝前や起床後に、**具体的な行動の提案を通知**する（例:「CO2が1,200ppm。寝る前に5分換気を」）。

### 1.3 成功指標（案）[TBD]
| 指標 | 目標（案） |
|---|---|
| 毎日のデータ欠損率（睡眠・環境の両方そろった夜の割合） | 90% 以上 |
| 睡眠効率（実睡眠時間 ÷ 就床時間） | 利用開始時から改善 |
| 就寝時刻のばらつき（標準偏差） | 利用開始時から縮小 |
| 提案通知のうち実行した割合（自己申告） | 50% 以上 |

## 2. スコープ

### 2.1 対象とするもの
| 区分 | 内容 |
|---|---|
| 健康テーマ | **睡眠の質**（最優先）。睡眠に影響する日中の行動（日光・運動・歩数）も補助的に扱う |
| データ源 | Apple Watch / iPhone のヘルスケア（HealthKit）、スマートホームセンサー（温度・湿度・CO2・照度・人感）、天気（任意） |
| 最適化の範囲 | **提案・通知まで**。家電の操作は人が行う |
| 利用者 | 当面は自分。**将来のサービス化を前提に設計**する（マルチユーザー対応できる構造、プライバシー配慮） |
| 画面 | **iPhone アプリのみ** |

### 2.2 対象外（現時点）
- 家電の自動制御（エアコン・照明の自動調整）。将来の拡張候補として[付録B](#付録b-将来の拡張候補)に記載。
- 病気の診断・治療・予防をうたう機能（睡眠障害の判定など）。医療機器プログラムに該当するおそれがあるため扱わない（[6.3](#63-法規制コンプライアンス)）。
- Web 版（パソコンのブラウザで見る画面）。将来の拡張候補として[付録B](#付録b-将来の拡張候補)に記載。
- Android / Wear OS 対応。
- 食事・体重管理など、睡眠に直接関係しない健康テーマ。

## 4. 扱うデータ

### 4.1 ヘルスケアデータ（HealthKit 経由）
HealthKit のデータは iPhone 端末内にあり、**クラウド API では取得できない**。iOS アプリで読み取り、サーバーへ送る必要がある。

| データ | HealthKit の型 | 用途 | 条件 |
|---|---|---|---|
| 睡眠ステージ（就床・覚醒・コア・深い・レム） | `sleepAnalysis` | 睡眠指標の計算の土台 | watchOS 9 以降 |
| 心拍数 | `heartRate` | 睡眠中の心拍推移 | — |
| 安静時心拍数 | `restingHeartRate` | 回復度合いの目安 | — |
| 心拍変動（HRV, SDNN） | `heartRateVariabilitySDNN` | 回復度合い・ストレスの目安 | — |
| 呼吸数 | `respiratoryRate` | 睡眠中の変化 | — |
| 手首皮膚温（睡眠中） | `appleSleepingWristTemperature` | 寝室の温度との関係 | Series 8 以降 / Ultra |
| 血中酸素 | `oxygenSaturation` | 参考値（診断には使わない） | 対応機種・地域のみ |
| 日光を浴びた時間 | `timeInDaylight` | 体内時計への影響 | watchOS 10 以降の対応機種 [要確認] |
| 歩数・アクティブカロリー・エクササイズ時間 | `stepCount` / `activeEnergyBurned` / `appleExerciseTime` | 日中の活動との関係 | — |
| 環境音の大きさ | `environmentalAudioExposure` | 寝室の騒音の参考値 | ノイズ測定がオンの場合 [要確認] |

補足:
- **Apple の「睡眠スコア」（watchOS 26）は、開発者向け API が公開されていない**（Apple Developer Forums の Apple 担当者の回答による）。そのため、睡眠ステージから**独自の睡眠指標を計算**する（[5.2](#52-睡眠指標の定義)）。
- 過去のヘルスケアデータは HealthKit に残っているため、**アプリが完成した時点で過去分を取り込める**（バックフィル）。

### 4.2 環境データ（スマートホームセンサー）
**取れるデータの種類が最も多い構成**にする。機器の構成は [デバイス選定](./device-selection.md) を参照。

| データ | 用途 | 取得元（SwitchBot） | 取得の目安 | 優先度 |
|---|---|---|---|---|
| 室温・湿度 | 睡眠への影響が大きい要因 | CO2センサー、ハブ3 | 5分間隔 | Must |
| CO2 濃度 | 換気不足による睡眠の質の低下を確認 | CO2センサー | 5分間隔 | Must |
| 部屋の明るさ | 就寝前の明るさ・睡眠中の暗さ | 人感センサー Pro（20段階）、ハブ3（10段階） | 5分間隔 | Must |
| 在床（ベッドに人がいるか） | 布団に入った・出た時刻。Apple Watch の「就床」との突き合わせ | 人感センサー Pro（止まっている人も検知） | 変化したとき（Webhook）＋5分間隔 | Must |
| 部屋の人の動き | 夜中に起きた時刻の補助 | ハブ3 | 変化したとき（Webhook） | Should |
| 窓・ドアの開閉 | 換気した時刻と CO2 の変化の関係。外出・帰宅の時刻 | 開閉センサー（窓・部屋のドア） | 変化したとき（Webhook）＋5分間隔 | Should |
| 照明の明るさ・色温度 | 就寝前の照明（明るさ・色）と寝つきの関係 | シーリングライト | 5分間隔 | Should |
| 加湿空気清浄機の運転 | 加湿・空気清浄をしていた時間と、湿度・睡眠の関係（消費電力から運転状態を推定する [要検証]） | プラグミニ | 5分間隔 | Should |
| カーテンの開閉 | 朝に日光を入れた時刻、夜の暗さ | カーテン3 | 5分間隔 | Could |
| 家電の使用（消費電力） | 就寝前のテレビ・パソコンの使用など | プラグミニ | 5分間隔 | Could |

- **環境データは後から取り込めない**（SwitchBot のクラウド API には履歴を取る手段がない）。そのため、**センサーを買ったらすぐに記録を始める**ことを最優先にする（[8章 Phase 0](#8-開発フェーズ案)）。
- SwitchBot では取れないデータ（エアコンの設定、騒音、正確なルクス、PM2.5 など）と補い方は [デバイス選定の5章](./device-selection.md#5-switchbot-では取れないデータと補い方) を参照。

### 4.3 その他
| データ | 取得方法 | 優先度 |
|---|---|---|
| 外の天気（気温・湿度・気圧） | 天気 API（WeatherKit など）[TBD]。屋外にセンサーを置かないため、外気はこれで取る | Should |
| 朝の体感（5段階）・メモ | アプリで手入力 | Should |
| 入浴した時刻 | アプリで手入力（ワンタップ）。風呂が共同でセンサーを置けないため | Should |
| カフェイン・飲酒などの行動 | アプリで手入力（ワンタップ） | Could |
| 目標就寝・起床時刻 | アプリで設定（Health アプリの睡眠スケジュールは API で読めないため）[要確認] | Must |

## 5. 機能要件

優先度: **Must**（MVPに必須） / **Should**（早めに入れたい） / **Could**（余裕があれば）

### 5.1 データ収集
| ID | 要件 | 優先度 |
|---|---|---|
| FR-101 | iOS アプリで HealthKit から 4.1 のデータを読み取る（ユーザーが許可した項目だけ） | Must |
| FR-102 | 新しいデータが記録されたら、バックグラウンドでサーバーへ送る（`HKObserverQuery` + バックグラウンド配信） | Must |
| FR-103 | 初回の連携時に、過去分（例: 最大90日）を取り込む | Should |
| FR-104 | サーバーがスマートホームのクラウド API から 5分間隔でセンサー値を取得する | Must |
| FR-105 | センサー API の利用回数の上限を超えないように取得間隔を調整する（SwitchBot は 1日 10,000 回。購入リストの9台を5分ごとに取ると 1日 約2,600 回） | Must |
| FR-106 | 取得に失敗したら再試行し、一定時間データが届かなければユーザーに知らせる | Should |
| FR-107 | 複数のメーカーに対応できるように、取得処理をメーカーごとに差し替えられる構造にする（アダプター方式） | Must（構造のみ。実装は1社から） |
| FR-108 | センサーと部屋（寝室・リビングなど）をひも付けて管理する | Must |
| FR-109 | SwitchBot の Webhook を受け取り、在床・人の動き・窓とドアの開閉の変化を**正確な時刻で**記録する（5分ごとの取得では、短い変化を見逃したり時刻がずれたりするため） | Should |

### 5.2 睡眠指標の定義
夜ごとに以下を計算する（定義は設計段階で確定する）。

| 指標 | 定義（案） |
|---|---|
| 就床時間 | 「就床」の開始から終了まで |
| 実睡眠時間 | コア + 深い + レム の合計 |
| 睡眠効率 | 実睡眠時間 ÷ 就床時間 |
| 入眠までの時間 | 就床の開始から最初の睡眠ステージまで |
| 中途覚醒 | 入眠後の覚醒の回数・合計時間 |
| ステージの割合 | 深い睡眠・レム睡眠の割合 |
| 睡眠中の心拍・HRV | 睡眠中の平均値と、個人の平常値（直近28日など）との差 |
| 就寝時刻のずれ | 目標就寝時刻・直近の平均との差 |
| 独自の睡眠スコア | 上記を組み合わせた 0〜100 の点数（重み付けは [TBD]） |

### 5.3 環境指標の定義
夜ごとに、**睡眠中**と**就寝前2時間**に分けて計算する。

| 指標 | 内容 |
|---|---|
| 室温・湿度 | 平均・最低・最高、目安の範囲を外れた時間 |
| CO2 | 平均・最高、1,000ppm を超えた時間 |
| 照度 | 就寝前の明るさ、睡眠中に明るかった時間 |
| 照明 | 就寝前2時間の照明の明るさ・色温度（暖色か寒色か）、消灯した時刻 |
| 在床 | 布団に入った時刻、布団に入ってから Apple Watch が入眠を記録するまでの時間、夜中に布団を出た回数 |
| 換気 | 窓・ドアを開けた回数・時間と、その前後の CO2 の変化。窓を開けて寝たか |
| 加湿・空気清浄 | 加湿空気清浄機を動かしていた時間（就寝前・睡眠中） |
| 入浴 | 入浴した時刻（手入力）と、就寝までの時間 |
| 帰宅 | 帰宅した時刻（ドアの開閉と在室から推定）と、就寝までの時間 |
| 朝の光 | カーテンを開けた時刻（起床時刻との差） |
| 日中の行動 | 日光を浴びた時間、歩数、エクササイズ時間 |

### 5.5 分析と気づき
| ID | 要件 | 優先度 |
|---|---|---|
| FR-501 | 環境の条件ごとに夜を分けて、睡眠指標を比べる（例: 室温 20〜22℃ の夜と 24℃ 以上の夜で、深い睡眠の割合を比べる） | Should |
| FR-502 | 比べる夜の数が少ないとき（例: 各グループ 7夜未満）は結論を出さず「データ不足」と表示する | Should |
| FR-503 | 違いの大きさと確からしさ（ばらつき）を一緒に示す。「〜の傾向がある」と表現し、因果関係は断定しない | Should |
| FR-504 | 季節・曜日・飲酒など、結果をゆがめる要因を考慮する（少なくとも曜日・季節で分けて見られる） | Could |
| FR-505 | データが溜まったら、ユーザー個人の「よく眠れる範囲」を推定し、通知の基準値に使う | Could |

### 5.6 提案と通知
| ID | 要件 | 優先度 |
|---|---|---|
| FR-601 | **就寝前の通知**: 目標就寝時刻の◯分前（初期値60分）に寝室の状態を確認し、目安を外れていれば具体的な行動を提案する | Must |
| FR-602 | **朝のレポート**: 起床を検知したら（睡眠データの同期後）、昨夜の要点を通知する | Must |
| FR-603 | **週のレポート**: 1週間の推移と、見つかった傾向をまとめて通知する | Should |
| FR-604 | **睡眠中は通知しない**（就寝時刻〜起床時刻、または睡眠中と判定している間） | Must |
| FR-605 | 同じ内容の通知は1晩に1回までにする | Must |
| FR-606 | 通知の種類ごとにオン・オフや時刻を変えられる | Must |
| FR-607 | 提案に「やった / やらなかった」を記録でき、その後の睡眠と比べられる | Could |

提案の目安値（初期値）: 個人のデータが溜まるまでは一般的な目安を使い、設定で変更できるようにする。

| 項目 | 初期の目安（案） | 根拠 |
|---|---|---|
| CO2 | 1,000ppm 以下 | 建築物衛生法の室内環境基準 [要確認] |
| 湿度 | 40〜60% | 一般的な目安 [要確認] |
| 室温 | 夏・冬で別の範囲を設定 | 設計段階で出典を確認して決める [要確認] |
| 就寝前の明るさ | 暗め（照度センサーの段階値で判定） | 機種ごとに段階値の意味を調べて決める |

提案文の例:
- 「寝室の CO2 が 1,250ppm です。寝る前に5分ほど換気しましょう」
- 「寝室が 26.5℃ です。あなたは 24℃ 以下の夜に深い睡眠が多い傾向があります」
- 「昨夜は寝る時刻がいつもより70分遅れました。今夜は 23:30 までに布団に入るのがおすすめです」
- 「寝室の照明が白っぽい色（6,000K）のままです。寝る1時間前なので、暖かい色に切り替えましょう」
- 「昨夜は布団に入ってから眠るまで45分かかりました。布団に入る前にスマホを置く時間を作ってみましょう」

## 6. 非機能要件

### 6.1 プライバシー・セキュリティ
| ID | 要件 |
|---|---|
| NFR-101 | 通信はすべて HTTPS（TLS 1.2 以上）で暗号化する |
| NFR-102 | 保存データ（DB・バックアップ）を暗号化する |
| NFR-103 | 集めるのは目的に必要なデータだけにする（使わない HealthKit の項目は読まない） |
| NFR-104 | ヘルスケアデータを広告・マーケティングに使わない、第三者に渡さない（App Store 審査ガイドライン 5.1.3） |
| NFR-105 | ヘルスケアデータを iCloud に保存しない（同ガイドライン 5.1.3）。自前サーバーへの保存は、同意とプライバシーポリシーを前提に行う |
| NFR-106 | 生成AI（LLM）で文章を作る場合は、外部に送る内容を最小限にし、事前に同意をもらう [TBD] |
| NFR-107 | 管理者がユーザーのデータを見る操作は記録を残す |

### 6.2 性能・信頼性・運用
| ID | 要件 |
|---|---|
| NFR-201 | 画面の表示は 2秒以内（30日分の推移グラフまで） |
| NFR-202 | 環境データの欠損は 1日あたり 5% 以内（センサーやネットワークの不調を除く） |
| NFR-203 | サーバーが止まっても、iOS アプリは再開時に未送信のデータを送り直す |
| NFR-204 | データは無期限に保存（ユーザーが削除するまで）。保存量の目安: センサー1台あたり 1日 288 件 |
| NFR-205 | 個人利用の段階では月額のサーバー費用を低く抑える（目安 [TBD]） |
| NFR-206 | 時刻はすべて UTC で保存し、表示時に利用者のタイムゾーンへ変換する |

### 6.3 法規制・コンプライアンス
| 項目 | 対応方針 |
|---|---|
| 医薬品医療機器等法（薬機法） | 病気の診断・治療・予防をうたわない「健康管理（ウェルネス）」の範囲にとどめる。「不眠症」「睡眠時無呼吸」などの判定や、医学的な効果の表現をしない |
| 個人情報保護法 | 利用目的を明示し、同意をもらう。健康に関するデータは「要配慮個人情報」と同じくらい慎重に扱う。海外のクラウドを使う場合は、外国にある第三者への提供に関する説明を行う [要確認] |
| 電気通信事業法（外部送信規律） | 分析ツールなどで外部にデータを送る場合、該当するかを確認し、必要なら公表する [要確認] |
| App Store 審査ガイドライン | 5.1.3（ヘルスケア）、5.1.1（アカウント削除など）に対応する |
| 利用規約・プライバシーポリシー | Phase 3（公開前）までに用意する |

## 7. システム構成（案）

```
┌──────────────┐   HealthKit    ┌──────────────────────┐
│ Apple Watch  │ ─────────────▶ │ iPhone アプリ（iOS）  │
└──────────────┘   （同期）      │ - HealthKit 読み取り  │
                                 │ - 画面表示・入力      │
                                 │ - 通知の受信          │
                                 └─────────┬────────────┘
                                           │ HTTPS
                                           ▼
┌──────────────┐  クラウドAPI   ┌──────────────────────┐
│ センサー      │ ─────────────▶ │ サーバー             │
│ (SwitchBot等) │  （5分ごと）    │ - API                │
└──────────────┘                 │ - センサー取得ジョブ  │
                                 │ - 分析ジョブ（毎朝）  │
                                 │ - 通知（APNs）       │
                                 │ - 時系列データベース  │
                                 └──────────────────────┘
```

- **iOS アプリが必須**: HealthKit は iPhone 上でしか読めないため。画面もすべて iPhone アプリで提供する。
- **サーバーが必要**: センサーの定期取得、夜をまたぐ分析、通知の送信をアプリ単体で安定して行うのは難しいため。
- 技術（v0.6 で決定。サービス化の段階で見直す）:

| 部分 | 技術 | 選んだ理由 |
|---|---|---|
| iOS アプリ | Swift / SwiftUI / Swift Charts | HealthKit を使うため（Phase 1 で作る） |
| サーバー | **Cloudflare Workers（TypeScript）** | 5分ごとの自動実行と Webhook の受け取りを、サーバーの管理なしで無料枠の範囲で動かせる |
| データベース | **Cloudflare D1（SQLite）** | Workers から直接使え、無料枠（保存 5GB）で数年分のセンサーの値が入る |
| 通知 | APNs（Workers から送る） | Workers から送れることを Phase 1 の最初に確かめる [要確認] |

Phase 0 のサーバーは [server/](../server/) にある（セットアップ手順は [server/README.md](../server/README.md)）。

## 8. 開発フェーズ（案）

| フェーズ | 目的 | 主な内容 | 完了の条件 |
|---|---|---|---|
| **Phase 0: 機器購入と記録開始** | 環境データを早く溜め始める | センサー購入・設置、センサー値を5分ごとに DB へ保存するサーバーを動かす（Webhook の受け取りも含む。**作成済み**: [server/](../server/)） | 寝室の温湿度・CO2・照度が毎日記録されている |
| **Phase 1: MVP（自分専用）** | 毎日使える最小限の形にする | iOS アプリ（HealthKit 読み取り・送信・過去分の取り込み）、Webhook の受信、睡眠指標の計算、ホーム・夜の詳細・推移の画面、就寝前の通知・朝のレポート | 2週間、毎朝レポートが届き、画面で確認できる |
| **Phase 2: 気づきと提案** | 自分にとっての最適条件を見つける | 体感・行動の記録、条件別の比較分析、週のレポート、個人の目安値の推定 | 30夜以上のデータから傾向が1つ以上示される |
| **Phase 3: サービス化の準備** | 他の人が使える形にする | Sign in with Apple、同意画面、データの書き出し・削除、2社目のセンサー対応、規約・ポリシー、TestFlight での試験配布 | 外部の試験ユーザーが自分で設定を完了できる |

Phase 0 を最初に置く理由: ヘルスケアデータは後から過去分を取り込めるが、**環境データは記録していない期間の分を後から取れない**。アプリを作っている間にもデータを溜めておけば、Phase 1 が終わった時点ですぐに分析を始められる。

## 9. 前提条件・制約
- 利用者は iPhone と Apple Watch を持ち、**寝るときも Apple Watch を着けている**こと（充電のタイミングを朝の身支度中などにずらす必要がある）。
- iOS アプリの開発には Mac と Xcode が必要 → **開発用の Mac（Apple M5、メモリ 32GB）あり**。
- サーバーからの通知（APNs）、TestFlight、App Store 公開には **Apple Developer Program（有料・年会費制）** への登録が必要。無料のアカウントでも自分の iPhone で動かせるが、通知が使えず、7日ごとにアプリを入れ直す必要があるため、Phase 1 の開始時に登録する想定。
- センサーのクラウド API の仕様・利用回数の上限はメーカーの都合で変わる可能性がある。
- センサーの照度は段階値（人感センサー Pro は 1〜20、ハブ3 は 1〜10）で、正確なルクスではない。照明の明るさ・色温度はシーリングライトの設定値で、日中の光は Apple Watch の「日光を浴びた時間」で補う。
- エアコンは赤外線リモコンで操作するため、設定温度や運転状態は SwitchBot から読み取れない。
- **住環境（初期ユーザー）**: 寮のワンルーム。寝る場所と、日中に過ごす場所が同じ部屋のため、照度や人感の値には日中の生活も含まれる。在床の判定は、人感センサー Pro をベッドだけに向けたうえで、Apple Watch の睡眠データと合わせて行う。
- **Wi-Fi**: SwitchBot のハブは、パスワードだけでつながる 2.4GHz の Wi-Fi（WPA2-PSK など）が必要。ブラウザでログインする Wi-Fi や、ID とパスワードで認証する企業向けの Wi-Fi（802.1X）にはつながらない（SwitchBot 公式サポートによる）。寮の Wi-Fi はパスワード方式の個人用で条件を満たすが、**当面は部屋に置くモバイル Wi-Fi を使う**。モバイル Wi-Fi は電池切れ・自動スリープ・通信量の上限で切れることがあるため、センサーのデータが途切れたら気づけるようにする（FR-106）。設定の注意は [デバイス選定の6.1](./device-selection.md#61-wi-fi) を参照。
- **寮の規則**: 照明の付け替えや、壁・窓枠へのテープでの取り付けが認められているかを確認する。退去時に元に戻せるよう、元の照明は保管し、はがせるテープを使う。

## 付録A: 用語
| 用語 | 意味 |
|---|---|
| HealthKit | iPhone のヘルスケアデータを読み書きするための Apple の仕組み |
| HRV（心拍変動） | 心拍の間隔のゆらぎ。高いほど回復している目安とされる |
| 睡眠効率 | 布団にいた時間のうち、実際に眠っていた時間の割合 |
| バックフィル | 過去のデータをまとめて取り込むこと |
| APNs | Apple のプッシュ通知の仕組み |
| アダプター方式 | メーカーごとの違いを吸収する部品を差し替えて、複数メーカーに対応する作り方 |

## 付録B: 将来の拡張候補
- **家電の自動制御**: 就寝前に照明を暗く・暖色にする、睡眠中の室温をエアコンで調整する（SwitchBot ハブの赤外線リモコン機能などを利用）。まずは提案の効果を確かめてから検討する。
- **Apple Watch アプリ**: 寝る前のチェックや朝の体感入力を Watch で行う。
- **Web 版**: パソコンのブラウザで推移や分析結果を見る。
- **家族での利用**: 同じ寝室を共有する人どうしでセンサーを共有する。
- **騒音センサー**への対応。
