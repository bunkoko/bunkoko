## 1. なぜ作り直すか

E20261124-01（形式B・北原白秋『フレップ・トリップ』）を ch2 まで聞いたオーナーの言葉：

- 「全体的に本の要約がないと、状況についていけず、感情移入ができない。本の背景から説明した後に、その人物のこんな状況ですと説明したい」
- 「創作物という観点で、その資料から得られる示唆や考え方を伝える必要があると思う。現在は事実だけを述べているようで、ほとんど得られるものがない」
- 「小説などの資料は、やはり台本の中で2つまでとし、小説でも同じような場面がありましたという参考程度にしてほしい。本筋は統計を用いたこの現代社会の分析にして欲しい」
- 「またである調にしたい」
- 統計について：「論文など統計を大量に入手できるところはない？圧倒的に不足している」

見終わった人に持ち帰ってほしいこと（オーナー）：

> まずは統計で現代社会の現状や過去の状況を知る。その後、小説や本などの文章を聞くことで、創作物でも同じことが考えられていたのかというふうに発見する。最終的にその対処法などもし調査することができればそれも提示する。対処法というのはマインドセットなどの考え方に加えてルーティンなどのシステム的な対策もあります。

今の作りが合わない理由（洗い出しで確かめた）：

- 形式 A〜D は4つとも古典が中心。統計の章は A の context だけで、統計は1章に2行まで（planner.py:580-591, 642）。
- 統計は 1 行 = 1 つの数（stats.csv、53 行）。「昔と比べる」ための、同じ調査・同じ問いの何年分かの数が無い。
- 背景の事実の台帳（config/facts.csv）は 0 行。自動の事実（生没年・初出・何年前か）しか無いので、背景の章が同じことの言い換えになった（E20261124-01 の ch1）。
- あらすじ・人物の状況を入れる仕組みが無い。
- 対処法に使える「試して効果を確かめた研究」は、研究の台帳 22 行のうち 1 行（FN-anger-reappraisal-2019）だけ。

## 2. ねらい・ねらわないこと・してはいけないこと

### ねらい
1. 回の本筋を「統計で今と昔を知る」にする。1 回に統計を 5〜8 点（今の値と、昔と比べる 2 点の組）使う。
2. 物語（小説・随筆・日記・詩・哲学、論語・自省録などの古典）は 1 回に 2 つまで。各作品の場面は 1 つ。背景 → あらすじ → 人物の状況 → 一節 → 語り手の示唆、の順で話す。
3. 最後に対処法を出す。考え方（マインドセット）と、決まった習慣などの仕組み（ルーティン）の両方。試して確かめた研究があればそれを、無ければ関係を調べた研究（関係として）と語り手の提案を使う。
4. 地の文はである調。
5. e-Stat から統計をまとめて取り込む（数はプログラムが写す）。

### ねらわないこと（v1 では作らない）
- 外国の統計（OECD・ILO・世界銀行）。規約を指標ごとに確かめる必要があり、オーナーは頼んでいない。
- 月ごとの統計。v1 は年・年度だけ。
- e-Stat の表を探すコマンド（getStatsList・getDataCatalog）。Claude がクラウドから e-Stat のサイトを見て探す（サイトの一覧に統計表 ID とファイルの ID が出ることを確かめた）。
- 論文をまとめて取る仕組み（OpenAlex・PMC・Crossref）。対処法の研究を増やすために要るが、統計の取り込みと形式 S が動いてから、別の設計で作る（§12）。
- 既存の stats.csv 53 行の作り直し。そのまま使う。
- 形式 A〜D の作り直し。`--format` で指定すれば今までどおり動けばよい。
- 昔の辞書の語釈（defs）を形式 S に付けること（Claude の判断：章の流れに置き場所が無い。あとで足せる）。
- 画面に「語り手の考え」と出す札（オーナーは頼んでいない）。

### してはいけないこと（作れても失敗）
- LLM が数・年・増え方を書くこと。比べる文はコードが作る。
- AI が統計の数を打ち込むこと。過去の年の数は、プログラムが e-Stat から写したものだけ。
- 権利判定（license.py、SPEC R1〜R8）、G1 の「統計の隣だけ」の決まり（D-035）を緩めること。
- 毎回同じ中身の繰り返しになって、YouTube の量産の判定に当たること（§6.9）。
- あらすじで結末を明かすこと。自死・自傷・病気などの除外カテゴリの話をあらすじで語ること。
- 対処法が、健康・医療・お金・法律の助言や「〜すれば楽になる」のような効き目の約束になること。

## 5. 段1 統計の系列の取り込み

### 5.1 考え方
- 1 つの「系列」＝ 1 つの調査 × 1 つの問い × 1 つの集団 × 1 つの単位の、年ごとの数。
- 数はプログラムが写す：
  - API の表は、Mac が e-Stat の API（net.py 経由・appId は .env）から取る。
  - API に無い・古い調査は、e-Stat のファイル（CSV・Excel。登録なしで取れる）からプログラムが読む。
- AI（クラウドの Claude）が書くのは「どの表・どの分類・どのセルか」と「何の数か（label）」と「調べ方の変わり目（breaks）」だけ。別の AI の見直し役が確かめる。
- オーナーが確かめるのは、回で使った系列の「何の数か・分類・変わり目」と、その回で読む比べる文（§5.6）。数そのものは確かめない（プログラムが写したため）。

### 5.2 データの置き場所（Claude の判断：Git に入れる。系列と数だけで小さい）
| ファイル | 中身 | 書く人 |
|---|---|---|
| config/stat_series.csv（Git） | 系列の定義 | `koten sources merge`（Claude の下書き → 見直し役 → オーナーの確かめ） |
| config/stat_points.csv（Git） | 年ごとの数 | `koten stats fetch`（Mac。ファイルの系列はクラウドでも `--check` で確かめるだけ） |
| docs/estat/<series_id>.json（Git。系列ごとに1つ。R17） | 表の情報（政府統計名・作成機関・表題と表番号・調査年月・公開日・最終更新日）と、**選んだ分類の符号と名前だけ** | `koten stats meta`／`stats fetch`（Mac） |
| HDD raw/estat/（Mac）、data/estat-cache/（クラウド、Git に入れない） | 取ったままの応答とファイル（net.py のキャッシュ） | net.py |
| SSD の stat_series・stat_points 表 | 上の CSV ＋ 読み込みのときに計算する値 | `koten db init` |

- 取ったままの応答は Git に入れない（大きなデータ）。docs/estat の JSON も全部の分類は入れず、選んだ符号の分だけ（地域の分類は数千あるため）。
- stat_points.csv が大きくなったら `stats fetch` が警告する（目安は builder が決める）。

### 5.3 config/stat_series.csv の列
- series_id：`[a-z0-9_]+`。stats.csv の stat_id と同じ名前は不可（db init が止める）。
- themes：config/themes.yaml の語を 1〜3 個（`;` 区切り）。
- label：何の数か（集団＋問い＋はかり方）。年・元号・数を入れない（どの年にも同じ文が合うように）。
- unit、survey（政府統計名）、publisher（作成機関）。
- source_kind：`estat_api` か `estat_file`。period_kind：`年` か `年度`。
- selector（JSON）：
  - estat_api：`{"statsDataId": "…", "cdTab": "…", "cdCat01": "…", …, "cdArea": "…"}`。時間の分類以外は、どの分類も符号を 1 つに決める。
  - estat_file：`{"parts": [{"statInfId": "…", "fileKind": 0, "updated": "YYYY-MM-DD", "sheet": "…", "values": "D12:R12", "periods_cells": "D5:R5" または "periods": ["2023"], "label_cells": ["A12", "D6"], "unit_cell": "A3"}]}`。1 つのファイルに何年分もあるときは 1 part、年ごとに別のファイルなら年ごとに part。
- table_title、url（API は `dbview?sid=…`、ファイルは最新のファイルの file-download の URL）。
- latest_known：その調査が出している最新の年（e-Stat のファイルの一覧から）。
- breaks（JSON）：`[{"before": "2020", "note": "令和2年から郵送（面接から）"}]`。根拠は where に書く。
- trend・trend_from・trend_to・trend_note：オーナーが確かめたときだけ（今の決まりと同じ）。
- status（`''`・`保留`）、checked_by（今と同じ「AI（調べ役と見直し役）」「オーナー」）、checked_at、checked_sha、where、note。

### 5.4 config/stat_points.csv の列
series_id、period（YYYY）、value（元の文字のまま。`,` を除いて数として読めること）、mark（`-`・`…`・`x`・`***` など。mark があるとき value は空）、part、src_label（ファイルの系列で、コードが読んだ見出しのセルの文字）、src_unit、fetched_at、src_sha。並びは (series_id, period)。

### 5.5 SSD で計算する値（db init）
- segment：比べてよい区切り。breaks の年と、ファイルの見出しの文字が前の年と違う年で区切る。
  （2026-11-27：オーナーの決め。見出しの言い方だけが違う年の境は、下書きの joins に両方の言い方と同じ問いである根拠を書けば区切らない。区切り（breaks）と見出しの分からない部分の境は今までどおり。見直し役が根拠を確かめ、オーナーがカードで確かめる。R44）
- value_num：数（mark のときは NULL。0 にしない）。period_label：「2004年」「2004年度」。
- latest_period、stale（latest_period が latest_known より古い）。
- check_sha：label・unit・selector・表の情報と分類の名前・数と mark・breaks から作る。owner_ok：checked_by が「オーナー」かつ checked_sha が今の check_sha と同じ。取り直して何かが変わると、オーナーの確かめは自動で外れる。
- stats.csv の 53 行は今の stats 表にそのまま入れる。系列の数は stats 表に写さない（Claude の判断：今のテストと A〜D の企画が変わらないように。読むのは §6.2 の resolve_key）。
- 読み込みは全部か何もしないか（今の load_stats と同じ）。themes の語・除外カテゴリの言葉（label・table_title・分類の名前）・selector の形・年の重なり・value と mark の両方・数として読めない value を確かめる。

### 5.6 確かめのページ（スマホ）
- 新しい種類「series」のカード。今の統計のカードの隣に足す。
- カードに出すもの：
  - その回で読む文（今の値の文と、**比べる文そのもの**。§6.3）
  - 元の資料の言葉：API は政府統計名・作成機関・表題（表番号）・調査年月・最終更新日・統計表 ID と、選んだ分類の「分類名：項目名」。ファイルは、ファイル名・シート・見出しと単位のセルの文字・公開日。
  - 年ごとの数の表（抜けた年・mark・変わり目に印）。ファイルの系列は、シートのその部分を HTML の表にして、数のセルを赤、見出しの行を黄色。
  - e-Stat の表・ファイルへのリンク。
  - 「数はプログラムが e-Stat から写した。確かめるのは、何の数か・分類・変わり目・読む文」の 1 行。
- 数は直せない。直せるのは label だけ。
- 確かめは系列ごと。一度確かめた系列は、check_sha が変わるまでほかの回でもそのまま使える。
- `koten sources todo` は、回で使った統計の記号（§6.2）を系列にまとめて書き出す。

### 5.7 コマンド
- `koten stats meta --drafts <下書き>`（Mac）：表の情報と分類を取って docs/estat に書く。
- `koten stats fetch [--series …] [--refresh] [--check]`：
  - API の系列は KOTEN_ESTAT_APPID が無ければ飛ばす（クラウド）。ファイルの系列はどこでも動く。
  - 系列ごとに、点の数・最新の年・抜け・mark・見出しの変化・単位・前と変わった数（「オーナーの確かめが外れる」）を出す。
  - `--check` は書かずに確かめるだけ。
  - コードが確かめること：API の単位・政府統計名・作成機関・表題が、系列の定義と同じか。時間の符号の頭4桁と名前が合うか。年・年度以外の時間の分類は断る。
- `koten stats list [--theme] [--stale] [--unchecked]`（SSD を読む）。
- `koten db init` が stat_series・stat_points も読む。
- `koten doctor` が「e-Stat の ID：設定済み／未設定」を出す（値は出さない）。
- 取り直しは手で月1回ほど（`stats fetch --refresh`）。`koten update` には入れない（Claude の判断）。

### 5.8 net.py
- `fetch(…, secret_params={"appId": …})`：秘密の値は送る引数にだけ入れる。マニフェストの URL・キャッシュの名前・エラーの文には出さない。保存する応答の中に同じ文字があれば `***` に置き換える。httpx の例外は秘密を消した文で投げ直す。
- `fetch_json(…, error_of=…)`：e-Stat の STATUS が 100 以上ならキャッシュを消して止める（今の MediaWiki と同じ形）。
- 間隔：e-stat.go.jp は 2 秒（settings の rate_limit）。
- Excel は openpyxl を足す（.xlsx だけ。.xls は要る表が出たときに考える）。（2026-11-27：要る表が .xls だけで出ていたので、.xls も xlrd で読む。R38）CSV があれば CSV を使う。CSV は utf-8-sig、だめなら cp932。

### 5.9 流れ（誰がどこで）
1. クラウドの Claude：e-Stat のサイトで表とファイルを探し、系列の下書き（docs/research/<日付>-source-drafts.json の series）を作る。DB の表とファイルの新しさを比べ、新しいほうを選ぶ。ファイルの系列は `stats fetch --check` で読めることを確かめる。別の AI の見直し役がページを開き直して label と変わり目を確かめる。
2. Mac：`koten stats meta --drafts …` → docs/estat を push。
3. クラウド：docs/estat を見て API の符号を埋め、`stats fetch --check` で確かめ、`sources merge --accept-rest` で stat_series.csv に入れる（AI が確かめた行）。push。
4. Mac：`koten stats fetch` → `koten db init` → stat_points.csv と docs/estat を push。
5. 回で使ったら、今と同じ `sources todo` → スマホで確かめ → `sources merge --todo`。

### 5.10 説明欄とグラフ
- 説明欄の「使った調査とデータ」に、系列ごとに「「調査名」（作成機関）使った年 URL」。
- グラフのカードを使ったら、資料ごとに「「調査名」（作成機関）を加工して作成」。
- API の系列を使った回は、e-Stat のクレジットの文「このサービスは、政府統計総合窓口(e-Stat)のAPI機能を使用していますが、サービスの内容は国によって保証されたものではありません。」を説明欄に自動で入れる。無ければ承認できない（VOICEVOX のクレジットと同じ）（Claude の判断：動画が「サービス」に当たるかは規約に書いていないので、安全なほうにした）。
- グラフ：比べる点の組には折れ線のカードを足す。その系列の、同じ区切りの年を並べ、比べる 2 点に印。抜けた年は空ける（線でつながない）。数は DB の文字のまま。% の縦軸は 0 から。グラフの形はコードが数から作る（外のものを読まない）。

### 5.11 受け入れ（段1）

## 6. 段2 形式 S の企画

### 6.1 形式 S（config/formats.yaml）
```yaml
S:
  name: 統計から考える
  description: 統計で今と昔を知り、同じような場面を描いた作品を1〜2つ読み、対処法を考える
  passages: {min: 1, max: 2}
  distinct_works: true
  chapters:
    - {role: opening,     target_sec: [30, 60]}
    - {role: stats_now,   target_sec: [150, 210]}
    - {role: stats_past,  target_sec: [120, 180]}
    - {role: story,       target_sec: [130, 190], facts: 2, fact_sec: [20, 30]}
    - {role: story_short, optional: true, target_sec: [80, 120]}
```

## 7. 段3a あらすじと人物の状況の台帳（背景の事実は §7.5）

### 7.1 2 つの台帳（Git の CSV → `koten story build` で SSD）
- config/synopses.csv：作品ごとに 1 行。synopsis_id = `SY-` + work_id（`:` を `-` に）。

  - text_ja：**である調**、2〜4 文。synopsis は 200 字まで、about は 150 字まで（Claude の判断：物語の章を 190 秒に収めるため）。
  - support（文ごとの根拠のチャンク）、evidence（文ごとに 160 字までの抜き出し 2 つまで。スマホのページで HDD なしに見せるため）、source_sha（本文の sha）、drafter、judge、status（draft／ai_checked／verified）、issues、checked_by、checked_at、note。

- 作るのは、回が使う作品と一節の分だけ（1 回に 1〜2 作品）。

### 7.2 下書き（Mac だけ。HDD を読む。企画・台本・API の途中では動かない）
`koten story draft --episode latest [--redo] [--id …]`
1. 企画を読み、物語の章の作品と一節について、行が無い・draft・sha が変わったものを作る。
2. 材料：HDD の texts.parquet・chunks.parquet。チャンクの頭に［c番号］の印を入れる。
   - あらすじ：本文が 30,000 字までなら全部を 1 回で。長い作品は 30,000 字までの区切りごとに、根拠つきの覚え書きを作り、最後にまとめる。
   - 人物の状況：一節の前 6,000 字と後 300 字。
   - 古典（canon。論語・自省録など）：その一節の確かめ済みの訳・解釈（SSD の renderings）と、同じ作品の前の 3 節。取り込んだ保護期間切れの英訳（Legge・Long など）も、下書きと判定の材料にだけ使ってよい。画面には出さない（Claude の判断：今の shiyaku と同じ扱い）。「どんな本か」は、本の文から分かること（誰の言葉を誰がまとめた形か、話題）だけ。状況は、その節の話し手・相手・話題が分かるときだけ作り、無ければ空でよい。
3. 下書きは Opus、見直しは Sonnet（今の shiyaku と同じ流れ：下書き → コードの確かめ → 1 文ずつの判定 → コードが結果を決める → 2 回まで書き直し）。
   - 判定役は、その文が根拠にしたチャンクの**区切りの本文をまるごと**（30,000 字まで）見て確かめる。長い作品も、どの文も本文と照らす（オーナーが選んだ「別の AI が本文と照らす」を守る）。長い作品で区切りを使ったことはカードに出す。
4. コードの確かめ（machine_issues）：空・長さ・文の数／です・ますの文末／「」『』／本文に無い数字／今の本（S4）の書名／人名の表の名前／死因の言葉・除外カテゴリの言葉（「安全：」で始まる issue）／本文の言い回しに近すぎる。
5. 書き方の決まり：あらすじは、始まりの状況・主な人物・主な出来事まで。**結末は書かない**。about は、本の文から分かること（形・語り手・話題）だけ。成り立ち・作者・時代は書かない（それは事実の台帳。R6）。人物の状況は、誰が・どこで・直前に何があったか。一節を言い直さない。
6. ウィキペディアは下書きにも判定にも渡さない（R2）。
7. ClaudeCLILLM に大きさの確かめを足す（引数が大きすぎるときは LLMError、OSError も受ける）。30,000 字（約 90KB）は Linux の 1 引数の上限 128KiB と macOS の上限の内側。

### 7.3 オーナーの確かめ
- いつ：台本のあと、音声の前に 1 回（Claude の判断：2026-11-24 の「回で使った行だけ」を守り、違うと押されても音声を作り直さずに済む）。形式 S では、企画が渡した統計の記号・あらすじ・状況は台本で必ず使う（使わないと書き直し。shape の検査）。研究は G1 の書き直しで外れることがあるので、台本で残ったものだけ。違うと押された行があれば、直してから台本を作り直し、それから音声へ。
- 回で使った行だけ。`sources todo` に synopses・scenes を足す。スマホのカードは、文ごとに根拠の抜き出しを出し、「合っている／違う＋ひとこと」。文は直さない（違うなら draft に戻り、ひとことを次の書き直しに渡す）。
- verified の行は、source_sha・span_sha が変わるまでほかの回でも使う。
- AI が確かめただけの行は、使ってよいが承認を止める（今の統計・研究と同じ）。
- 正規化で本文が変わった作品は、`forget-works --changed --apply` で行を draft に戻す。

### 7.4 安全

### 7.5 本の背景の事実（オーナー：Q4 の b）

  1. Mac：`koten facts todo --episode latest`（今のコマンド）で、その回の作品・作者に要る事実の一覧を書き出して push。今の `facts draft`（ウィキペディアを手がかりにした下書き）もそのまま使える。
  2. クラウド：Claude が、事実ごとにウィキペディア以外の資料を開いて確かめ、資料の URL・ページの名前・どこに書いてあるかを付けた下書きを作る。別の AI の見直し役が同じ資料を開き直して確かめる。`sources merge` で facts.csv に「AI（調べ役と見直し役）」の行として入れる。
  3. Mac：`facts build` → `facts attach --episode latest` → `script`。
  4. 回で使った事実は、`sources todo` に入り、スマホの「事実」のカードで確かめる（文・資料へのリンク・どこに書いてあるか）。確かめるまで承認できない。

- カードには資料の文を写さない（リンクとどこに書いてあるかだけ）。写してよいのは、保護期間の切れた本文と、政府の資料だけ。
- 書き換える決まり：SPEC R6、D-012、CLAUDE.md の背景の行（「確認済みの事実」に AI が確かめた事実が入り、回で使ったものは承認の前に人が確かめる、と書く）。
- 足りない許可先（文学館などのホスト）は、要るときにこの環境の許可先に足すお願いを出す。

  - 「この研究で調べたのは、{{finding_pop:ID}}である。」

### 8.3 章ごとの書き方（writer.py の ROLE_NAMES・ROLE_GUIDE に足す）
- 見出しはコードが章ごとに決まった言い方を入れる（今の G1 は「統計」「データ」「調査」を見出しで禁じている。言い方は builder が決める。例：「いま、何が起きているか」「昔と比べると」「物語の中の同じ場面」「どうすればいいか」）（Claude の判断：禁止は緩めない）。
- opening：悩みの言葉（30 秒以内）と、この回の流れ（統計 → 物語 → 対処法）の予告。
- stats_now：統計の段落と語りの段落をかわるがわる置く（G1 の「統計の隣だけ」を守る）。語りは、その数が暮らしの中で何を意味するかを、数を書かずに話す。
- stats_past：比べる文（コード）と語り。続く動きはオーナーの trend があるときだけ。
- story：① 背景（事実の記号。20〜30 秒）→ ② あらすじ（{{synopsis:ID}}）→ ③ 人物の状況（{{scene:ID}}）→ ④ 一節 → ⑤ 語り手の示唆（統計で見た今と、物語の場面を重ねる）。⑤ の前に、前の章で使った統計の記号を 1 つだけもう一度置いてよい（統計に触れる文が G1 の「統計の隣だけ」を通るように）。brief も書き手に渡す。
- story_short：あらすじ → 一節 → 示唆。
- coping：企画の枠の順に、研究があれば研究の決まった言い方、無ければ語り手の提案。
- summary：統計で見たこと・物語の発見・対処法を 1 つずつ短く。今の「今日からできる小さな一歩」は coping と重なるので外す。
- ending：「古典の一節で」の言い方を外す。

### 8.4 語り手の考え
- 語り手の考え（示唆・読み・提案）は、その文に「私は」「私には」「私の考えでは」「私の見方では」を入れるか、段落の頭を「ここからは私の考えだ。」にする。コードで確かめる（Claude の判断）。
- 語り手の考えとして、統計が社会について何を示すかを読んでもよい。ただし新しい事実・数・研究は足さない。
- 作者のねらい・気持ちを事実のように言わない（AUTHOR_INTENT の検査を足す）。
- 提案は効き目を約束しない。健康・医療・お金・法律の言葉を使わない（EFFECT_CLAIM の検査を足す：効果がある・効く・改善・解消・治る・予防、「〜すると／すれば … 楽になる・軽くなる・眠れる・減る・消える・前向きになる」など）。

### 8.5 検査の変更（どれも止める方向。script_v6 のとき）
- である調の言い伝え：と言われている・とされている・と考えられている・と指摘されている・と報告されている・という説がある・〜そうだ・とよく聞く・ことが分かった、などを止める（今は です・ます の形だけ止めていて、である調の形は通ってしまう）。
- 移り変わり：増えた・減った・多く（少なく）なった・高まった・深まっている・上がった・下がった・「昔より」「〜年前と比べ」「この〇十年で」＋変わる言葉を、社会の話として止める（自分の話の例外は今のまま）。「二十年前」「30年前」のような 2 桁・漢数字の年数も止める。比べる文（コードの統計の段落）は止めない。
- 研究の文の後ろの決まった言い方に、である調の形と「」を足す（BACKREF）。
- 「」に入れてよい記号に fact（記号だけのとき）・finding・finding_limits・finding_pop を足す。それらの文は「」に入っていなければ止める。
- あらすじ・状況の記号は、文の頭に置く。台帳の文を記号なしで書き写したら止める。物語の章の外で使えない。
- 1 文ずつの判定（judge_v5）をする章に stats_now・stats_past・story・story_short・coping・summary を足す。あらすじ・状況の行を判定役に〔ID〕つきで見せる。文の種類に「語り手の考え（opinion）」を足す。
- 長さ：一節・統計の段落・あらすじ・状況・「」の台帳の文は、書き手が短くできない字として数える。G7 の章の範囲は formats.yaml から（今と同じ）。
- G1 で直らずに残ったら、今と同じく回を止める（対処法の章を外して進めることはしない）（Claude の判断）。
