## 実装時の判断

### 2026-10-21 青空文庫の権利判定（license.py・ingest/aozora.py）

- 作品・人物の著作権フラグが1つでも「あり」なら COPYRIGHTED、「なし」以外の値（空欄など）があれば UNKNOWN。
- フラグがすべて「なし」でも、著者・訳者の没年で R3 を重ねて確かめる（1968年以降の没者がいれば COPYRIGHTED）。権利ルールは緩める方向に変えないため、二重に判定する。
- 作品CSVには国籍が無い。訳者がいる作品の原著者は外国人とみなし「国籍不明」として扱い、1958〜1967年没なら NEEDS_REVIEW（R4。自動で満了にしない）。訳者がいない作品の著者は日本人とみなす。
- 没年で判定するのは著者と訳者だけ。編者・校訂者などは青空文庫のフラグで判定する。
- NEEDS_REVIEW の作品は、人が PD_JP と確認するまで本文を保存しない（R2 と同じ扱い。書誌情報のみ works.parquet に残す）。

### 2026-10-21 正規化とチャンク化

- text_norm は「空白・改行の除去」「全角英数記号→半角」「半角カナ→全角」だけ。NFKC は互換漢字（U+F900台）を変えるので全体には使わない。
- 外字注記：`U+XXXX` があればその文字、`第3水準1-r-c`／`第4水準2-r-c` があれば JIS X 0213（euc_jis_2004）から実字にする。どちらも無ければ〓に置き換え、texts.parquet の gaiji 列に元の注記と置換結果を残す。
- 見出しは `［＃「…」は（同行・窓）大／中／小見出し］` と `［＃中見出し］…［＃中見出し終わり］` を読む。下位の見出しは「大 / 中」のようにつなげて section にする。複数行にわたる見出し（ここから見出し）は未対応。
- くの字点の代用表記 `／＼`・`／″＼` は 〳〵・〴〵 に置き換える。
- チャンクは段落を max_chars まで詰める。1段落が max_chars を超えるときは文末（。！？＋閉じ括弧）で切り、1文が max_chars を超えるときだけ文の途中で切る。
- 2026-10-22 追記：実データで16字のチャンクが出た（短い段落の直後に長い段落）。min_chars 未満のチャンクは、前か後ろとつなぎ、つなぐと max_chars を超えるときは隣のチャンクと文の切れ目で分け直す（段落の途中で分かれることがある）。章が丸ごと min_chars 未満のとき（後記など）はそのまま残す。ランダムな文章3,000通りで、max_chars 超え・文の途中での切断・本文の取りこぼしが無いことを確かめた。
- 原本の保存先は raw/aozora/ 以下に公式URLと同じパス（cards/<人物ID>/files/<zip>）。manifest.jsonl には実際に取得したURL（ミラー）を書く。

### 2026-10-21 取得（net.py）

- 外部アクセスは net.Fetcher だけを通す。1ホストあたりの間隔は rate_limit.per_host_per_sec、manifest にあるURLは再取得しない（--refresh-list のときは ETag で条件付き取得）。
- 1件の取得失敗では止めず、失敗を表示して次へ進む。works.parquet の raw_path が空の作品は次回の実行で取り直す。
- User-Agent は settings.toml の http.user_agent。連絡先を自分のものに書き換えてから実データを取得する。

### 2026-10-22 M2：引用候補・埋め込み・索引

- **一節の照合**：LLM が書き写した一節は、まず原文の完全一致で探し、無ければ空白・改行・全角半角の揺れだけを無視して探す。見つかった位置の原文をそのまま quote_text として保存するので、保存済みの引用は必ず原文と一致する（SPEC §8.3「部分文字列でなければ破棄」を満たす）。言葉が1字でも違えば捨てる。
- **捨てる条件**（理由ごとに件数を表示）：原文に無い、長さが20〜120字の外、同じ位置の重複、要旨が空か60字超、統制語彙のテーマが無い、20字以内の悩みが無い。統制語彙に無いテーマと、20字を超える悩みは、その項目だけ外す。quotability は0〜1に丸める。
- **再試行**：JSON として読めない・形が違うときだけ再試行（2回まで）し、だめなら done に failed として残す。LLM に接続できないときは、そこまでの結果を保存して止める（全チャンクを failed にしない）。
- **再開**：augment/<llm>/<prompt版>/ に part-NNNNN.parquet（候補）と done-NNNNN.parquet（処理済みチャンク）を batch_size ごとに書く。候補を先に、done を後に書くので、途中で落ちたバッチは未処理として次回やり直す。Ctrl+C でも、それまでのバッチは保存してから止まる。
- **埋め込み**：emb/<embed_model>/ に shard-NNNNN.npy（float16）と ids を書く。meta.json にどの augment の候補かを記録し、別の候補で上書きしそうなときは止める。
- **密ベクトル索引**：100万件以下は内積の全探索なので、FAISS（IndexFlatIP）と同じ結果を numpy で計算する。Python 3.14 で faiss-cpu の wheel が無い恐れがあるため。100万件を超えたら FAISS の近似索引を足す。
- **BM25**：自前の Okapi BM25（k1=1.5、b=0.75）を CSR 形式で SSD に保存。分かち書きは SudachiPy（モードC、正規化形、助詞・助動詞・記号を除く）。SudachiPy が無いときは settings の bm25.tokenizer を bigram にする。
- **候補表（SSD）**：cache/candidates.parquet は、使用可（R1）の作品の候補だけに、作品名・著者・license・review_required・文字遣いを付けたもの。caution は残し、検索（M4）で外す。
- **API**：create_app は SSD の場所と埋め込みモデル名だけを受け取り、HDD のパスを持たない。索引が無いときも起動し、/healthz が no_index を返す。待ち受けは 127.0.0.1 の api.port（既定 8765）。
- **重い依存**：sentence-transformers・SudachiPy は `uv sync --extra ml` で入れる任意の依存にした（テストは簡易埋め込み HashEncoder と bigram で動く）。

### 2026-10-22 ベクトルストアの比較（D-009）

規模は最大50万件・1024次元（SPEC §5）。検索では、注意フラグ・直近10回の作品・直近5回の著者・1冊回の作品指定・テーマなどで絞り込む（SPEC §3・§8.6）。日本語の BM25 と組み合わせる。

| 方式 | 絞り込み | 正確さ | 日本語のキーワード検索 | 置き場所・運用 |
|---|---|---|---|---|
| numpy 全件計算＋真偽の配列（採用） | 列から作った配列でスコアを消すだけ。条件は Python で自由に書ける | 全件計算なので取りこぼし無し | 自前の BM25＋SudachiPy | Parquet・npy を SSD に置くだけ。依存が増えない |
| FAISS | IDSelector を検索パラメータで渡す必要があり面倒 | IndexFlatIP なら全件計算で numpy と同じ。近似索引は取りこぼしあり | 無い | Python 3.14 の wheel に不安 |
| Chroma | where 句で書ける | HNSW の近似検索 | 日本語の分かち書きは無い | 独自の保存形式（SQLite＋HNSW）に、Parquet と二重に持つことになる |
| LanceDB | SQL 風の where で事前に絞れる | 全件計算か近似索引を選べる | 全文検索はあるが日本語は工夫が要る | Arrow 系なので Parquet と相性が良い。将来の候補 |
| Qdrant | 絞り込みが最も強い | HNSW | 疎ベクトルで対応 | サーバー（Docker）が要り、この規模には大きすぎる |

測定（このクラウド環境の4コアCPU、50万件・1024次元・絞り込みあり）：float16 のまま検索のたびに変換すると約1.26秒／回、float32 でメモリに持つと約50ms／回。そこで索引は SSD に float16 で置き、読み込むときに float32 にする（約2GB。メモリ32GBで問題ない）。

100万件を大きく超える、または検索が遅くなったら、LanceDB への移行を検討する（Chroma より Parquet・Arrow と相性が良く、事前の絞り込みができる）。

### 2026-10-22 ローカルLLMの呼び方（Ollama）

- `--limit 20` の比較（Mac・メモリ32GB、OpenAI 互換API・思考モードの指定なし）：gemma4:26b と qwen3.5:27b は1回の応答が300秒を超えて時間切れ。gemma3:27b は完走したが1チャンク48.4秒（候補32件、捨てた一節6件）。約12万チャンクでは約67日かかり、このままでは使えない。

- think を受け付けないモデルには、think を外して送り直す。
- 時間切れは「LLM の呼び出しに失敗」として、そこまでの結果を保存して止める。

### 2026-10-24 M4：検索と企画

- **クエリ**：悩みの文・言い換え（40字以内）・HyDE（理想の一節の要旨、80字以内）の3つ。テーマは悩みマスターのものを優先し、LLM のものを足す（統制語彙だけ）。結果は SQLite の query_cache に控え、同じ悩み・同じモデル・同じプロンプト版なら LLM を呼ばない。LLM の出力が壊れ続けたら悩みの文だけで検索し、plan_json の queries に fallback=true を残す。
- **埋め込みの接頭辞**：悩みの文と言い換えは "query: "、HyDE は一節の要旨なので候補と同じ "passage: " で埋め込む。
- **RRF**：6つのリスト（3クエリ×密ベクトル・BM25、各100件）を k=60 で統合し、上位50件。絞り込み（caution・直近10回の作品・直近5回の著者）は検索の段階でかけるので、統合の前に外れる。
- **リランク**：SPEC は「上位10件に並べ替える」だが、形式A は別々の作品が4つ以上要るので、50件すべてに点を付けて並べ替え、そこから作品が重ならないように10件の候補（shortlist）を作る。
- **MMR**：候補の中身ではなく作品・著者の重なりで多様性を取る（A・C は1作品1つ、D は1著者3つまで）。B は1作品なので重なりを見ない。
- **最終選択**：LLM に shortlist から選ばせ、理由（60字以内）を付けさせる。候補に無い ID・数・作品の重複・悩みの割り当て・D の2人の対立の条件を検める。満たさなければ検索の順位で選び、理由にそう書き、plan_json の selected_by を search_rank にする。ただし D（対立する2つの考え）は検索の順位では対立を決められないので、LLM が選べなければ企画を作らない。
- **形式ごとの入力**：A・B・D は悩み1つ。B は悩みに合う候補の多い作品（上位10作品まで）から一節が4つ以上そろうものを選び、その作品のテーマを持つほかの悩みを足して3〜5の悩みに当てはめる。C はテーマ（または悩みの最初のテーマ）から、優先度の高い代表の悩み3つを選ぶ。
- **章立て**：formats.yaml に一節を割り当て、尺の目安は各章の範囲の真ん中から始めて合計12分に近づける。研究の章（optional）は論文が入る M8 まで入れない。まとめ（D は compare）の章に人の一言の枠（human_take）を1つ置く。統計は context の章に、悩みのテーマと同じテーマの stat_id を2つまで入れる。章の切れ目を広告位置の候補として ad_break_after_chapters に残す（秒は音声のあと）。
- **保存**：`koten plan` は回を planned で episodes に入れ、使う一節を usage（role=main）に、悩みの last_used_at を記録する。`--dry-run` で保存しない。`--format` を省くと、同じ形式が3回続かないようにし、使っていない形式から順に試す。
- **評価**：`koten eval export` が優先度の高い代表の悩み20件について、5つのやり方（密ベクトルだけ・BM25だけ・ハイブリッド・＋HyDE・＋リランク）の上位10件を合わせて、順番を混ぜた印付け用の CSV（tests/eval/retrieval.csv、Excel で開けるよう BOM 付き）を書く。すでに付けた点は残す。`koten eval retrieval` が nDCG@10・Recall@20・上位10件の未判定の割合を出す。評価では再使用間隔をかけない。埋め込みモデルの比較は、別のモデルで索引を作って同じ評価を回す。

### 2026-10-24 検索の評価の点を2値にし、Claude Haiku の grader で人の点と突き合わせる

- **点は2値**（利用者の判断）：1＝合う、0＝合わない。人も LLM もぶれずに付けられるようにする。nDCG@10・Recall@20 は2値でも計算できる。前の版の 2 は 1 として読む。
- **grader**：Mac の Claude Code を `claude -p` で呼び、ログイン中のサブスクリプションで Haiku を使う（API キーは使わない）。`claude --help`（利用者の Mac）で確かめた指定：`--model haiku`、`--output-format json`、`--json-schema`、`--system-prompt`、`--tools ""`（ツールなし）、`--no-session-persistence`、`--safe-mode`（CLAUDE.md・MCP・プラグインを読まず、ログインはそのまま）。`--bare` は API キーでしか認証しないので使わない。子プロセスには ANTHROPIC_API_KEY を渡さず（API の課金に切り替わらないように）、空のフォルダで動かす。
- 確認済み（2026-10-24、利用者の Mac で `claude -p --model haiku --output-format json --json-schema ...`）：`--json-schema` の結果は structured_output に JSON のまま入り、result にも同じ内容が文字列で入る。`--model haiku` は claude-haiku-5-5 になった。サブスクリプションのログインで動き、約2秒で返った。total_cost_usd は定価で計算した参考の金額（costBasis: list）。koten は structured_output を先に読み、無ければ result の文を JSON として読む。
- **呼び方**：悩み1つぶんの一節（20〜30件）をまとめて1回で判定させる。答えが抜けた一節は2回までやり直し、悩み1つ終わるごとに CSV に保存する（止めても判定済みは残る）。判定の基準は「共感・別の見方・前へ進むヒントのどれかを与え、動画でこの悩みと結び付けて紹介できるか」。迷ったら合わない。要旨より原文を優先して読ませる（要旨を書いた gemma の癖に引きずられないように）。
- **一致の確かめ**：`koten eval agreement` が、人と LLM の点が両方ある行で一致率・コーエンのκ・食い違いの一覧を出す。κ 0.6 以上なら、LLM の点を広い評価（悩み50件、設定を変えたときの比較）に使ってよい目安とする。
- **gemma のファインチューニング**：今はしない。検索の順位を決めるのは埋め込みとリランクで、gemma は言い換え・HyDE・最終選択の担当のため。26B を 32GB の Mac で学習させるのはメモリが厳しく、学習データも要る。nDCG の基準を測ったあと、足りなければ人と Haiku の点を学習データにしてリランク（または埋め込み）の学習を先に考える。

### 2026-10-25 M5：台本と検証ゲート

- **LLM**：台本は Claude Sonnet、G3 の判定は Claude Haiku。どちらも Mac の Claude Code（`claude -p`）をサブスクリプションで呼ぶ（SPEC は Claude API だが、利用者の希望で API キーを使わない。settings.toml の llm.script・llm.judge で API に戻せる）。
- **章ごとに書かせる**：LLM に書かせるのは章タイトルと段落の並び（語り・一節・統計）だけ。段落の ID、画面の種類（語り→写真、一節→引用カード、統計→グラフ、章の頭→章タイトルカード）、一節の読み方（新字新仮名の日本語は原文、それ以外は「画面は原文・読みは現代語」）、章の出典一覧、人の一言の枠、紹介する本の一覧は企画と DB から機械的に決める。
- **プレースホルダ**：{{quote:}}・{{source:}}（著者『作品』「章」）・{{author:}}・{{title:}}・{{stat:}}（内容は値（調査、年））・{{worry:}}。{{quote_ja:}}（外国語の自前訳）は M8 まで解決できない（使えば G1 で落ちる）。
- **G1**：解決できない記号、一節・統計の段落に記号以外、割り当てた一節がちょうど1回出ていない、語りの「」の中が一節でも悩み文でもない（10字以下の語の強調と、一節・悩み文の一部をそのまま引くのは許す）、著者名（2字以上）・『作品名』の直書き（章タイトルも）、統計の数字の直書き。不合格の章は問題を伝えて書き直させ（2回まで）、直らなければその時点で止めて回を error にする。
- **G3**：一節を持つ章と、作品紹介・まとめ・比べる章を、別の呼び出し（Haiku）で判定する。一節と前後の文脈にない事実（著者の経歴・年号など）を書いていれば不合格。不合格の章は書き直させ（2回まで）、直らなければ回は止めずに review_required（人の確認へ）。

- **保存**：episodes の script_json・verification_json・review_required・state（script_done か error）・state_msg。`koten script --show` で差し込んだ台本を読める。script_done 以降の回を作り直すときは --force。
- **SSD の候補表**に底本（base_book）と URL を足した（出典の表示用。次の `koten index build` から入る）。
- `koten episode discard` で回を discarded にすると、再使用間隔・30日のクラスタ間隔・形式の連続の数え方から外れる（試しに作った回のため）。悩みの last_used_at は戻さない（優先度の「新しさ」が下がったままになる）。

### 2026-10-25 M5 の実データ（E20261025-01、Opus・xhigh）で見つかったことと直したこと

- 結果：G1・G2・G4・G5・G6 合格、G3 は ch6 が3回の書き直しでも通らず「人の確認へ」。文字数4,861字で見積もり約16分12秒（上限15分を超える）。旧仮名の一節（正岡子規『墨汁一滴』・横瀬夜雨『五葉の松』）は「画面は原文・読みは現代語」になった。
- **G3 が通らなかった原因は正規化の不具合**：高神覚昇『般若心経講義』の「同行小見出し」（見出しのすぐ後ろに同じ行で本文が続く）の行を、行ごと見出しとして扱っていた。そのため章の名前に本文が丸ごと入り、{{source:}} を差し込むと長い本文が出典に混ざった。G3 はそれを「文脈にない長い引用」と正しく指摘した。あわせて、その行の本文はどのチャンクにも入っておらず、付加情報づけから抜けていた。
  - 直し方：見出しの注記の終わりで行を分け、後ろの本文は次の行の本文にする（同行見出し・窓見出し）。後ろに本文の無い普通の見出しは text_orig が変わらない。
  - 安全策：{{source:}} の章の名前は30字で切る（…を付ける）。
- **作り直しの手順**（全件の augment が終わってから）：`koten normalize aozora` が、前回から本文か章が変わった作品を clean/aozora/changed_works.json に足す → `koten chunk aozora` → `koten forget-works --changed`（数えるだけ）→ `--apply` で、その作品の候補・処理済みの記録・埋め込みを取り除く → `koten augment`（その作品のチャンクだけ）→ `koten embed` → `koten index build`。候補の ID は作り直しても同じになりうるので、その作品の一節を使っている回（discarded 以外）が残っていれば forget-works は止まる。
- **章の長さ**：G1・G3 が通ったあと、差し込んだ文字数を目安（target_sec × 1分300字）と比べ、±30%（script.length_tolerance）を超えたら直し方（何字削る・足す）を伝えて書き直させる（G1・G3 と同じ2回まで）。一節だけで上限を超える章は問わない。直らなかった章は verification の length_estimate.notes に残す（尺の本当の確かめは音声のあとの G7）。

### 2026-10-25 尺と、視聴回数に効く要件（D-011）

**調べたこと**（YouTube の説明。この環境から support.google.com は開けなかったので、検索結果の抜粋で確かめた）

- おすすめは、クリック・再生時間・アンケート・共有・高評価・低評価から学ぶ。アンケートは動画を1〜5の星で聞き、4〜5の星だけを「価値のある再生時間」として数える。2011年に「クリックしても見たとは限らない」と分かり、2012年に再生時間を足した（[YouTube の仕組み：おすすめ](https://www.youtube.com/howyoutubeworks/product-features/recommendations)、[On YouTube's recommendation system](https://blog.youtube/inside-youtube/on-youtubes-recommendation-system/)）。
- 動画の長さそのものを有利・不利にするという公式の説明は見つからなかった。解説記事も「決まった最適な長さは無い。中身に必要なだけの長さにする」という立場が多い。
- ミッドロール広告は、収益化した8分以上の動画に入れられる。既定では自然な切れ目に自動で入る（[YouTube ヘルプ：長い動画のミッドロール](https://support.google.com/youtube/answer/6175006)）。
- YouTube Studio の「維持率の重要ポイント」では、イントロ＝30秒時点で見ている人の割合。50%以上なら「平均以上のイントロ」。比べる相手は「同じくらいの長さの直近10本」。イントロが低いときは、タイトルとサムネイルを中身に合わせ、最初の30秒を変えるよう勧めている（[YouTube ヘルプ：維持率の重要ポイント](https://support.google.com/youtube/answer/9314415)）。
- 「テストと比較」で、タイトルとサムネイルを3つまで試せる。勝ちはクリック率ではなく総再生時間の割合で決まる（[YouTube ヘルプ：タイトルとサムネイルの A/B テスト](https://support.google.com/youtube/answer/16391400)）。
- 2025-07-15 から、収益化の「繰り返しの多いコンテンツ」が「独自性のないコンテンツ」（量産・繰り返し）に改められた（SPEC §2 の量産型対策と同じ向き）。

**決めたこと**

1. **尺**：G7（音声のあと）は10〜15分のまま。目標は12分。
   - 下限10分：ミッドロールの8分に2分の余裕を持たせる（読み上げの速さの補正や章の伸び縮みで8分を割らないように）。
   - 上限15分：長さそのものはおすすめで有利にならない。1回の一節は4〜6（形式Dは2〜4）で、1つに1分半〜3分かけると10〜14分になる。それより長くすると水増しになり、維持率と満足（アンケート）を下げる。台本の利用枠と、人の確認の時間も増える。
   - 台本の段階：章ごとに目安の±30%で書き直させる（前の記録）のに加え、回全体の見積もりが10〜15分の外なら「視聴の注意」として確認画面に出す（回は止めない）。プロンプトに「水増ししない」を足した（script_v2）。
   - 見直し：公開10本ごとに、Studio の平均視聴率・平均視聴時間・イントロを尺と形式で比べ、範囲を変えるか決める（M9）。
2. **冒頭30秒**（台本の段階で確かめる）：最初の30秒（1分300字なら150字）のうちに {{worry:}} で悩みを言う。オープニングで挨拶・チャンネル・高評価の話をしない。合わなければ書き直させ、直らなければ「視聴の注意」。
3. **タイトル案**（台本の段階で確かめる）：悩みの言葉を前に置く。差し込んだあとで40字以内。著者名・作品名は {{author:}}・{{title:}} の記号で書かせる（R6 と同じく DB から差し込む）。「絶対・必ず・衝撃・激変・人生が変わる・最強・知らないと損」を使わない（クリックが増えても、見て満足されなければ推薦に載らない）。オープニングの章に、この回で読む作品と記号の対応を渡す。直らなければ悩みから作る仮のタイトル（「悩み――古典の一節で考える」）にし、「視聴の注意」に出す。台本JSONの title は記号のまま持ち、`--show` と公開用キットで差し込む。
4. **サムネイルとタイトルの A/B**（M6 の公開用キット）：1回につき、サムネイル3枚（別々のテンプレート）とタイトル案3つを作り、Studio の「テストと比較」に掛けられるようにする。サムネイルの文字は悩みの言葉を短く、タイトルと同じ約束をする。
5. **終わり方**（M6）：エンディングは45秒以内で、長いあいさつで締めない。終了画面（最後の5〜20秒）と固定コメントで、同じテーマの公開済みの回を1本すすめる。テーマ別の再生リストに入れる（次の動画へつなぐ）。
6. **説明欄**（M6）：最初の2行に、悩みの言葉と「この回で分かること」を書く。チャプターは章の開始時刻から作る（D-007）。
7. **公開後**（M9）：Studio の CSV から、インプレッションのクリック率・平均視聴時間・平均視聴率を回ごとに取り込み、30秒時点の維持率も取れる範囲で取り込む。形式・尺・タイトルの型で比べる。

**しないこと**：総再生時間を増やすために尺を伸ばす。中身と違うことを約束するタイトルやサムネイル。ここに挙げた数（40字・30秒・NG の言い方）は YouTube の決まりではなく、この企画の決まり。公開後の数字で直す。
