## 実装時の判断

### 2026-10-21 青空文庫の権利判定（license.py・ingest/aozora.py）

- 作品・人物の著作権フラグが1つでも「あり」なら COPYRIGHTED、「なし」以外の値（空欄など）があれば UNKNOWN。
- フラグがすべて「なし」でも、著者・訳者の没年で R3 を重ねて確かめる（1968年以降の没者がいれば COPYRIGHTED）。権利ルールは緩める方向に変えないため、二重に判定する。
- 作品CSVには国籍が無い。訳者がいる作品の原著者は外国人とみなし「国籍不明」として扱い、1958〜1967年没なら NEEDS_REVIEW（R4。自動で満了にしない）。訳者がいない作品の著者は日本人とみなす。
- 没年で判定するのは著者と訳者だけ。編者・校訂者などは青空文庫のフラグで判定する。
- NEEDS_REVIEW の作品は、人が PD_JP と確認するまで本文を保存しない（R2 と同じ扱い。書誌情報のみ works.parquet に残す）。

### 2026-10-21 正規化とチャンク化

- text_norm は「空白・改行の除去」「全角英数記号→半角」「半角カナ→全角」だけ。NFKC は互換漢字（U+F900台）を変えるので全体には使わない。
- 外字注記：`U+XXXX` があればその文字、`第3水準1-r-c`／`第4水準2-r-c` があれば JIS X 0213（euc_jis_2004）から実字にする。どちらも無ければ〓に置き換え、texts.parquet の gaiji 列に元の注記と置換結果を残す。
- 見出しは `［＃「…」は（同行・窓）大／中／小見出し］` と `［＃中見出し］…［＃中見出し終わり］` を読む。下位の見出しは「大 / 中」のようにつなげて section にする。複数行にわたる見出し（ここから見出し）は未対応。
- くの字点の代用表記 `／＼`・`／″＼` は 〳〵・〴〵 に置き換える。
- チャンクは段落を max_chars まで詰める。1段落が max_chars を超えるときは文末（。！？＋閉じ括弧）で切り、1文が max_chars を超えるときだけ文の途中で切る。
- 2026-10-22 追記：実データで16字のチャンクが出た（短い段落の直後に長い段落）。min_chars 未満のチャンクは、前か後ろとつなぎ、つなぐと max_chars を超えるときは隣のチャンクと文の切れ目で分け直す（段落の途中で分かれることがある）。章が丸ごと min_chars 未満のとき（後記など）はそのまま残す。ランダムな文章3,000通りで、max_chars 超え・文の途中での切断・本文の取りこぼしが無いことを確かめた。
- 原本の保存先は raw/aozora/ 以下に公式URLと同じパス（cards/<人物ID>/files/<zip>）。manifest.jsonl には実際に取得したURL（ミラー）を書く。

### 2026-10-21 取得（net.py）

- 外部アクセスは net.Fetcher だけを通す。1ホストあたりの間隔は rate_limit.per_host_per_sec、manifest にあるURLは再取得しない（--refresh-list のときは ETag で条件付き取得）。
- 1件の取得失敗では止めず、失敗を表示して次へ進む。works.parquet の raw_path が空の作品は次回の実行で取り直す。
- User-Agent は settings.toml の http.user_agent。連絡先を自分のものに書き換えてから実データを取得する。

### 2026-10-22 M2：引用候補・埋め込み・索引

- **一節の照合**：LLM が書き写した一節は、まず原文の完全一致で探し、無ければ空白・改行・全角半角の揺れだけを無視して探す。見つかった位置の原文をそのまま quote_text として保存するので、保存済みの引用は必ず原文と一致する（SPEC §8.3「部分文字列でなければ破棄」を満たす）。言葉が1字でも違えば捨てる。
- **捨てる条件**（理由ごとに件数を表示）：原文に無い、長さが20〜120字の外、同じ位置の重複、要旨が空か60字超、統制語彙のテーマが無い、20字以内の悩みが無い。統制語彙に無いテーマと、20字を超える悩みは、その項目だけ外す。quotability は0〜1に丸める。
- **再試行**：JSON として読めない・形が違うときだけ再試行（2回まで）し、だめなら done に failed として残す。LLM に接続できないときは、そこまでの結果を保存して止める（全チャンクを failed にしない）。
- **再開**：augment/<llm>/<prompt版>/ に part-NNNNN.parquet（候補）と done-NNNNN.parquet（処理済みチャンク）を batch_size ごとに書く。候補を先に、done を後に書くので、途中で落ちたバッチは未処理として次回やり直す。Ctrl+C でも、それまでのバッチは保存してから止まる。
- **埋め込み**：emb/<embed_model>/ に shard-NNNNN.npy（float16）と ids を書く。meta.json にどの augment の候補かを記録し、別の候補で上書きしそうなときは止める。
- **密ベクトル索引**：100万件以下は内積の全探索なので、FAISS（IndexFlatIP）と同じ結果を numpy で計算する。Python 3.14 で faiss-cpu の wheel が無い恐れがあるため。100万件を超えたら FAISS の近似索引を足す。
- **BM25**：自前の Okapi BM25（k1=1.5、b=0.75）を CSR 形式で SSD に保存。分かち書きは SudachiPy（モードC、正規化形、助詞・助動詞・記号を除く）。SudachiPy が無いときは settings の bm25.tokenizer を bigram にする。
- **候補表（SSD）**：cache/candidates.parquet は、使用可（R1）の作品の候補だけに、作品名・著者・license・review_required・文字遣いを付けたもの。caution は残し、検索（M4）で外す。
- **API**：create_app は SSD の場所と埋め込みモデル名だけを受け取り、HDD のパスを持たない。索引が無いときも起動し、/healthz が no_index を返す。待ち受けは 127.0.0.1 の api.port（既定 8765）。
- **重い依存**：sentence-transformers・SudachiPy は `uv sync --extra ml` で入れる任意の依存にした（テストは簡易埋め込み HashEncoder と bigram で動く）。

### 2026-10-22 ベクトルストアの比較（D-009）

規模は最大50万件・1024次元（SPEC §5）。検索では、注意フラグ・直近10回の作品・直近5回の著者・1冊回の作品指定・テーマなどで絞り込む（SPEC §3・§8.6）。日本語の BM25 と組み合わせる。

| 方式 | 絞り込み | 正確さ | 日本語のキーワード検索 | 置き場所・運用 |
|---|---|---|---|---|
| numpy 全件計算＋真偽の配列（採用） | 列から作った配列でスコアを消すだけ。条件は Python で自由に書ける | 全件計算なので取りこぼし無し | 自前の BM25＋SudachiPy | Parquet・npy を SSD に置くだけ。依存が増えない |
| FAISS | IDSelector を検索パラメータで渡す必要があり面倒 | IndexFlatIP なら全件計算で numpy と同じ。近似索引は取りこぼしあり | 無い | Python 3.14 の wheel に不安 |
| Chroma | where 句で書ける | HNSW の近似検索 | 日本語の分かち書きは無い | 独自の保存形式（SQLite＋HNSW）に、Parquet と二重に持つことになる |
| LanceDB | SQL 風の where で事前に絞れる | 全件計算か近似索引を選べる | 全文検索はあるが日本語は工夫が要る | Arrow 系なので Parquet と相性が良い。将来の候補 |
| Qdrant | 絞り込みが最も強い | HNSW | 疎ベクトルで対応 | サーバー（Docker）が要り、この規模には大きすぎる |

測定（このクラウド環境の4コアCPU、50万件・1024次元・絞り込みあり）：float16 のまま検索のたびに変換すると約1.26秒／回、float32 でメモリに持つと約50ms／回。そこで索引は SSD に float16 で置き、読み込むときに float32 にする（約2GB。メモリ32GBで問題ない）。

100万件を大きく超える、または検索が遅くなったら、LanceDB への移行を検討する（Chroma より Parquet・Arrow と相性が良く、事前の絞り込みができる）。

### 2026-10-22 ローカルLLMの呼び方（Ollama）

- `--limit 20` の比較（Mac・メモリ32GB、OpenAI 互換API・思考モードの指定なし）：gemma4:26b と qwen3.5:27b は1回の応答が300秒を超えて時間切れ。gemma3:27b は完走したが1チャンク48.4秒（候補32件、捨てた一節6件）。約12万チャンクでは約67日かかり、このままでは使えない。
- 対策として Ollama は独自の /api/chat で呼ぶ（provider = "ollama"）。think = false で思考モードを止め、num_ctx（4096）と num_predict（1024）に上限を付け、format に JSON スキーマを渡す。応答の prompt_eval_count・eval_count・各時間から、入力・出力のトークン数と生成速度を表示し、遅い原因を切り分ける。
- think を受け付けないモデルには、think を外して送り直す。
- 時間切れは「LLM の呼び出しに失敗」として、そこまでの結果を保存して止める。

### 2026-10-23 SD カード（exFAT）の ._ ファイル

- 全件の augment が `chunks/._aozora.parquet` を読もうとして止まった。Mac は exFAT などに書いたファイルの付帯情報を `._<名前>` の隠しファイルとして作る。
